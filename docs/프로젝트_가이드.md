# 대치스카이부동산 통합 프로그램 — 프로젝트 가이드

> 작성일: 2026-09-15
> 이 문서는 실제 코드(`main_app.py`, `desktop_app.py`, `*_core.py`, `*_app.py`, `DaechiSkyRealEstate.spec`, `.claude/launch.json` 등)를 직접 확인해서 작성했습니다.
> 기존 `PROJECT_ANALYSIS.md`(2026-09-08 작성)는 그 이후 추가된 `main_app.py`, `chrome-extension/`, `dist_package/`, `requirements.txt`, Git 초기화 등을 반영하지 못한 과거 스냅샷입니다. 최신 기준은 이 문서입니다.

## 1. 프로젝트 개요

대치스카이부동산에서 실제 업무에 사용하기 위해 장기적으로 개발 중인 부동산 업무용 통합 프로그램입니다. Python + Streamlit으로 화면을 만들고, PyInstaller로 Windows 데스크톱 실행 파일(`DaechiSkyRealEstate.exe`)로 패키징합니다.

일회성 프로그램이 아니라 앞으로 계속 기능이 추가되는 것을 전제로 합니다. 현재는 네이버 부동산 데이터 수집과 아파트 실거래가 조회 2가지 기능이 구현되어 있고, 앞으로 매물관리, 고객/상담관리, 계약관리, 학원 중개, 상가/건물 업무, 투자분석 등이 추가될 예정입니다.

## 2. 현재 기능

| 기능 | 담당 파일 | 설명 |
|---|---|---|
| 로그인 / 통합 진입점 | `main_app.py` | 직원 이름+전화번호로 로그인 후 두 기능 중 하나를 선택 |
| 네이버 부동산 수집 | `naver_land_app.py` + `naver_land_core.py` | 네이버 부동산 단지 검색, 매물 목록 수집, 중개사 광고 조회, 엑셀 내보내기 |
| 아파트 실거래가 조회 | `apt_trade_app.py` + `apt_trade_core.py` | 국토교통부(MOLIT) 오픈API로 매매/전월세 실거래가 조회, 차트, 엑셀 내보내기 |
| (보조 도구) 네이버 부동산 CLI 수집기 | `naver_land_scraper.py` | 화면 없이 특정 단지 하나를 커맨드라인에서 수집하는 독립 스크립트. 앱 실행 흐름에는 포함되지 않으며, 필요할 때만 직접 실행하는 보조 도구 |
| (보조 도구) 네이버 부동산 "오늘 등록" 필터 | `chrome-extension/naver-land-today-filter/` | 크롬 확장 프로그램. 네이버 부동산 웹사이트를 볼 때 오늘 등록된 매물만 걸러서 보여줌. Python 코드와는 데이터를 주고받지 않는 완전히 별개의 도구 |

## 3. 프로그램 실행 구조

### 실제 배포된 exe를 실행했을 때
```
DaechiSkyRealEstate.exe  (PyInstaller, 시작 파일 = desktop_app.py)
  └─ desktop_app.py: 자기 자신을 "--server-child" 옵션으로 다시 실행
       └─ 그 자식 프로세스가 Streamlit 서버를 띄움 (main_app.py 를 서빙)
            └─ main_app.py: 로그인 화면 표시
                 → 로그인 성공 시 "데이터수집" / "실거래확인" 버튼으로 화면 전환
                 ├─ [데이터수집] naver_land_app.py 실행 → naver_land_core.py 로직 사용
                 └─ [실거래확인] apt_trade_app.py 실행 → apt_trade_core.py 로직 사용
                                                          (.streamlit/secrets.toml 의 API 키 사용)
  └─ desktop_app.py(부모 프로세스): 위 서버 주소를 pywebview 네이티브 창으로 띄워서 보여줌
  └─ 창을 닫으면 자식 서버 프로세스도 함께 종료
```

### 개발 중 테스트할 때 (`.claude/launch.json`에 정의된 3가지 실행 방법)
- `python -m streamlit run main_app.py --server.port 8505` — 통합 앱 (로그인 포함, 실제 운영 화면과 동일)
- `python -m streamlit run naver_land_app.py` (포트 8501) — 네이버 부동산 화면만 단독 실행 (로그인/공통 스타일 없이 빠르게 확인용)
- `python -m streamlit run apt_trade_app.py --server.port 8502` — 실거래가 화면만 단독 실행

`naver_land_app.py`, `apt_trade_app.py`는 자체적으로 `st.set_page_config`를 호출하지 않습니다. "통합 진입점인 main_app.py에서 한 번만 호출한다"고 코드에 명시되어 있어, 정식 화면 설정(테마, 사이드바 숨김 등)은 `main_app.py`를 통해 실행할 때만 적용됩니다.

## 4. 기능별 구조

각 기능은 **로직(core.py)과 화면(app.py)이 분리**되어 있고, 두 기능은 서로를 import하지 않는 완전히 독립된 구조입니다 (이미 잘 되어 있는 부분이라 유지할 가치가 있습니다).

```
naver_land_core.py (577줄)  ←  naver_land_app.py (754줄)   [네이버 부동산 도메인]
apt_trade_core.py  (617줄)  ←  apt_trade_app.py  (1244줄)   [아파트 실거래가 도메인]
```

- `naver_land_core.py`: 네이버 부동산 인증 토큰 추출, 단지/매물 검색 API 호출(`NaverLandAsyncSession`), 가격/데이터 정제 로직.
- `apt_trade_core.py`: 국토부 실거래가 오픈API 호출, 시/군/구·동 코드 조회(`sigungu_codes.json`, `dong_codes.json` 사용), API 키 로딩(`resolve_service_key`).
- `naver_land_scraper.py`: `naver_land_core.py`를 그대로 재사용하는 37줄짜리 CLI 스크립트. 문서화된 보조 도구지만, 현재 어디에서도 자동 호출되지는 않습니다. **모듈 구조로 이전할 때 이 파일을 포함시킬지는 아직 결정하지 않았으며, 실제 이전 검토 대상입니다.**

`features/apt_trade/`, `features/naver_land/` 폴더가 이미 만들어져 있지만 **현재는 완전히 비어 있고 코드에서 전혀 참조되지 않습니다.** 공식 아키텍처 원칙은 이후 `modules/<도메인>/` 구조로 확정되었으며(10번 참고), 이 `features/` 폴더들의 처리 방향은 별도 승인 후 결정합니다.

또한 이 원칙에 따라 **`modules/naver_land/`, `modules/apt_trade/`, `modules/property/`, `modules/customer/`, `modules/consultation/`, `modules/academy/`, `modules/commercial/`, `modules/market/` 빈 폴더가 프로젝트 루트에 이미 생성되어 있습니다.** 다만 전부 빈 폴더이며, `naver_land_*.py`/`apt_trade_*.py` 등 실제 Python 파일은 하나도 옮겨지지 않은 상태입니다(자세한 이전 계획은 10번 참고).

## 6. 주요 의존관계

```
desktop_app.py
   └─ (subprocess) streamlit.web.cli → main_app.py

main_app.py
   ├─ st.Page("naver_land_app.py")
   └─ st.Page("apt_trade_app.py")

naver_land_app.py  → import naver_land_core as core
apt_trade_app.py   → import apt_trade_core as core

apt_trade_core.py  → sigungu_codes.json, dong_codes.json, .streamlit/secrets.toml (API 키)
naver_land_scraper.py → import naver_land_core as core   (독립 실행, 위 흐름과 무관)
```

두 기능(naver_land ↔ apt_trade) 사이에는 **어떤 방향으로도 import가 없습니다.** 완전히 독립적으로 동작하므로, 한쪽을 고쳐도 다른 쪽이 깨질 위험이 구조적으로 낮습니다.

## 7. 설정 및 secrets

- API 키(국토부 서비스키 등)는 `.streamlit/secrets.toml`에 저장하며, `apt_trade_core.py`의 `resolve_service_key`가 읽어옵니다.
- 로그인 인증 정보(직원별 아이디 → 비밀번호)도 같은 파일의 `[credentials]` 섹션에 저장되어 있으며, `main_app.py`는 `st.secrets["credentials"]`로 읽어옵니다. 소스 코드에는 더 이상 실제 비밀번호가 들어 있지 않습니다. (실제 값은 이 문서에도 적지 않습니다.)
- `secrets.toml`은 `.gitignore`에 포함되어 Git에 올라가지 않습니다. **임의로 이 파일의 구조(키 이름 등)를 바꾸지 마세요** — 코드에서 특정 키 이름을 그대로 참조합니다.
- `.streamlit/config.toml`은 테마 설정만 있습니다(색상 등). 서버 포트 등은 `.claude/launch.json`이나 `desktop_app.py`에서 커맨드라인 인자로 지정합니다.
- 주의할 점: PyInstaller 빌드 시 `.streamlit/` 폴더 전체가 통째로 exe에 포함되므로, 아파트 실거래가 기능의 API 키가 네이버 부동산 기능만 쓰는 빌드에도 함께 들어갑니다. 지금 당장 문제는 아니지만, 기능이 늘어나고 서로 다른 API 키를 쓰게 되면 키 관리 방식을 다시 검토할 필요가 있습니다.

## 8. 빌드 구조

- `DaechiSkyRealEstate.spec`이 PyInstaller 빌드 설정이며, 시작 파일은 `desktop_app.py`입니다.
- 이 spec 파일의 `datas`에는 `main_app.py`, `naver_land_app.py`, `naver_land_core.py`, `apt_trade_app.py`, `apt_trade_core.py`, `sigungu_codes.json`, `dong_codes.json`, `.streamlit/` 폴더 전체가 포함되어 있습니다. **새 파일을 추가하거나 기존 파일을 옮길 때는 이 목록도 함께 업데이트해야 빌드된 exe에서 정상 동작합니다.**
- `hiddenimports`에는 `naver_land_core`, `apt_trade_core`가 명시되어 있습니다. 새 기능의 core 모듈을 추가하면 여기도 추가해야 할 수 있습니다.
- 빌드 결과물: `build/`(중간 산출물), `dist/DaechiSkyRealEstate.exe`(최종 실행 파일) — 둘 다 `.gitignore`에 포함되어 있어 Git에는 올라가지 않습니다.
- `dist_package/`는 배포판(exe + 소스 복사본 + 사용자 가이드 + zip)을 모아둔 폴더입니다. **`.gitignore`에 이미 포함되어 Git에는 올라가지 않습니다.** 다만 안에 있는 소스 복사본은 원본 코드와 자동으로 동기화되지 않는 수동 스냅샷이므로, 최신 소스와 다를 수 있다는 점은 계속 유의해야 합니다.

## 9. 개발 원칙 (앞으로 새 기능을 추가할 때 지킬 기준)

1. **각 업무 영역은 `modules/<도메인>/` 아래 독립 모듈로 관리한다.** 새 기능은 가능하면 처음부터 이 구조로 만든다. 기존의 `~_core.py` + `~_app.py` 방식(지금의 naver_land, apt_trade)은 모듈로 이전하는 과도기에서만 쓰는 형태다. (현재 상태와 이전 계획은 10번 "향후 확장 방향" 참고)
2. **모듈(도메인)끼리 서로 직접 import하지 않는다.**
3. **프로그램 전체에서 쓰는 `common`/`shared`/`utils` 같은 공통 모듈은 기본적으로 만들지 않는다.** 정말 여러 모듈에서 동일한 기능이 실제로 반복되고, 공통화하는 것이 독립 모듈 구조보다 명확히 유리한 경우에만 먼저 사용자에게 설명하고 승인받은 후 공통화한다. 단순히 코드가 비슷하다는 이유만으로 공통 모듈을 만들지 않는다.
4. **`main_app.py`에는 로그인/네비게이션 외의 업무 로직을 넣지 않는다.** 업무 로직은 항상 해당 모듈의 core.py에 둔다.
5. **파일을 새로 만들거나 옮길 때는 다음 3곳을 함께 확인한다:** `DaechiSkyRealEstate.spec`(datas/hiddenimports), `.claude/launch.json`, `main_app.py`의 `st.Page` 경로.
6. **`.streamlit/secrets.toml`의 구조(키 이름 형식)를 임의로 바꾸지 않는다.** 새 API 키나 인증정보가 필요하면 기존 `resolve_service_key`, `[credentials]` 섹션과 같은 기존 방식을 재사용해 추가한다. API 키, 비밀번호 등 민감정보는 코드에 직접 저장하지 않는다.
7. **빌드 산출물(`build/`, `dist/`, `dist_package/`)은 Git에 커밋하지 않는다.**
8. **새 기능을 추가하거나 구조를 바꿀 때마다 이 문서(`docs/프로젝트_가이드.md`)와 `CLAUDE.md`를 함께 갱신한다.**
9. **더 이상 쓰지 않는 파일은 방치하지 말고 상태를 명확히 한다.** (예: "보조 CLI 도구로 유지", "이전 검토 대상", "삭제 예정" 등)
10. **사용자 승인 없이 파일이나 폴더를 삭제하지 않는다.** 사용하지 않는 파일/폴더가 발견되어도 먼저 실제 사용 여부와 삭제 필요성을 설명하고 승인을 받는다.
11. **기존 기능을 모듈로 옮길 때는 한 번에 하나의 모듈만 이전한다.** 여러 모듈을 동시에 이동/수정하지 않는다.
12. **모듈 이전은 다음 순서로 검증한다:** (1) 파일 이전 → (2) import/경로 수정 → (3) 해당 모듈 단독 실행 테스트 → (4) 통합 앱 실행 테스트. **정상 확인 전에는 다음 모듈로 넘어가지 않는다.**
13. **실제 이전 작업 전에는 현재 상태를 기준점으로 확보한다** (예: `git status`로 작업 트리가 깨끗한지 확인, 필요하면 먼저 커밋).
14. **과도한 추상화를 피한다.** 여러 모듈에서 실제로 동일한 기능이 반복되고, 공통화하는 것이 독립 모듈 구조보다 명확히 유리한 경우에만 사용자에게 먼저 설명하고 승인받은 후 공통화한다.
15. **Git 커밋/푸시는 사용자가 명시적으로 요청할 때만, 그리고 구조 변경의 경우 정상 동작 검증 후에 진행한다.** 의미 있는 작업 단위로 자주 커밋하는 것을 권장한다.

## 10. 향후 확장 방향 — 아키텍처 원칙: `modules/<도메인>/` 구조

지금은 실제로 동작하는 기능이 2개뿐이라 루트 폴더에 `도메인_core.py` + `도메인_app.py` 형태로 두는 방식이 크게 불편하지 않습니다. 하지만 계획대로 매물관리, 고객/상담관리, 계약관리, 학원 중개, 상가/건물 업무, 투자분석 등이 계속 추가되면 루트 폴더에 파일이 너무 많이 쌓여 찾기 어려워집니다.

**공식 목표 구조**: 각 업무 기능을 `modules/<도메인>/` 아래 독립된 폴더로 구성한다. 각 모듈은 하나의 독립된 업무 단위로 취급하며, 가능한 한 다음 영역을 자체적으로 관리한다: UI, 비즈니스 로직, 데이터 처리, 설정, 컴포넌트.

**현재 상태 (2026-09-15 기준)**: 아래 8개 모듈 폴더는 **이미 빈 폴더로 생성되어 있습니다.** 다만 전부 빈 상태이며, `naver_land_*.py`/`apt_trade_*.py` 등 실제 Python 파일은 하나도 옮겨지지 않았습니다. "모듈 이전이 완료됐다"는 뜻이 아니라, 앞으로 옮겨 담을 자리만 미리 만들어둔 상태입니다.

```
modules/
├─ naver_land/       (빈 폴더 — 지금은 naver_land_app.py / naver_land_core.py가 루트에 있음)
├─ apt_trade/        (빈 폴더 — 지금은 apt_trade_app.py / apt_trade_core.py가 루트에 있음)
├─ property/         (빈 폴더 — 매물관리, 신규 기능 예정)
├─ customer/         (빈 폴더 — 고객관리, 신규 기능 예정)
├─ consultation/     (빈 폴더 — 상담관리, 신규 기능 예정)
├─ academy/          (빈 폴더 — 학원 중개업무, 신규 기능 예정)
├─ commercial/       (빈 폴더 — 상가/건물 업무, 신규 기능 예정)
└─ market/           (빈 폴더 — 투자/물건 분석, 신규 기능 예정)

main_app.py      # 진입점 + 로그인 + 메뉴/페이지 연결만 (개별 업무 로직 금지)
desktop_app.py   # 패키징 실행기
```

**모듈 내부 파일 구성**: 기본은 다음 2개 파일입니다.

```
modules/<도메인>/
├─ app.py
└─ core.py
```

필요한 경우에 한해 해당 모듈 안에서만 `components.py`, `config.py`, `trade.py`, `rent.py`, `scraper.py` 등을 추가로 둘 수 있습니다. 어떤 파일을 추가할지는 실제 이전/개발 시점에 모듈별로 판단하며, 지금 미리 모든 모듈의 내부 구성을 확정하지 않습니다. (예: `naver_land_scraper.py`를 `modules/naver_land/`에 포함시킬지는 아직 결정하지 않았고, 실제 이전 단계에서 현재 역할을 다시 확인한 후 정합니다 — "이전 검토 대상"으로 남겨둡니다.)

- 모듈 간 직접적인 의존성은 최소화한다. 가능하면 한 모듈이 다른 모듈의 내부 구현에 직접 의존하지 않는다.
- 프로그램 전체에서 쓰는 `common`, `shared`, `utils` 등의 공통 모듈은 처음부터 만들지 않는다. 여러 모듈에서 동일한 기능이 실제로 반복되고, 공통화하는 것이 독립 모듈 구조보다 명확히 유리한 경우에만 사용자에게 먼저 설명하고 승인받은 후 공통화한다.
- 이전 검토 단계에서 만들어졌던 빈 `features/apt_trade/`, `features/naver_land/` 폴더는 이 `modules/` 원칙이 확정되기 전의 이름이며, 실제 마이그레이션 대상은 아닙니다. 이 폴더들을 어떻게 정리할지(삭제 또는 `modules/`로 대체)는 별도로 사용자 승인 후 결정합니다.
- 기존 `naver_land_*.py`, `apt_trade_*.py`를 실제로 `modules/naver_land/`, `modules/apt_trade/`로 옮기는 작업은 파일 이동에 따라 `DaechiSkyRealEstate.spec`, `.claude/launch.json`, `main_app.py`의 `st.Page` 경로를 모두 함께 수정해야 하므로, **지금 당장 진행하지 않고 별도의 작업으로 사용자 승인 후 진행합니다.**
- 실제 이전을 시작하면, 모듈을 한 번에 하나씩만 옮기고 다음 순서로 검증합니다: (1) 파일 이전 → (2) import/경로 수정 → (3) 해당 모듈 단독 실행 테스트 → (4) 통합 앱 실행 테스트. 정상 확인 전에는 다음 모듈로 넘어가지 않습니다. 이전 작업을 시작하기 전에는 `git status`로 현재 작업 상태를 기준점으로 확보해 둡니다.
